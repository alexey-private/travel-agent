# S5 — PDF-экспорт с корректным ивритом

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ответ агента на иврите экспортируется в PDF читаемым: слова в правильном порядке, числа и латиница не вывернуты, абзацы выровнены по правому краю, колонки таблиц идут справа налево.

**Architecture:** pdfkit рисует глифы ровно в том порядке, в каком они лежат в строке, и Unicode Bidirectional Algorithm не реализует. Поэтому перед отрисовкой каждая строка переводится из логического порядка (как текст набран) в визуальный (как он должен выглядеть) — это делает `bidi-js`. Иврит, в отличие от арабского, не требует glyph shaping, так что переупорядочивания и зеркалирования скобок достаточно. Перенос строк делается **до** переупорядочивания и вручную, потому что UBA применяется к каждой визуальной строке отдельно — если отдать перенос на откуп pdfkit, он разрежет уже перевёрнутый текст и получится каша.

**Tech Stack:** pdfkit, `bidi-js@1.0.3`, DejaVuSans, Jest.

**Spec:** [2026-08-28-i18n-hebrew-design.md](../specs/2026-08-28-i18n-hebrew-design.md) — §6.

## Global Constraints

См. [индекс планов](2026-08-28-i18n-hebrew-index.md#global-constraints). Важное именно здесь:

- `bidi-js@1.0.3` типов не поставляет — нужен локальный `.d.ts`.
- ~~**У `bidi-js` нет функции `getReorderedString`.**~~ **Неверно:** в `bidi-js@1.0.3`
  она есть и делает ровно то, что нужно, — разворот сегментов плюс подстановка
  зеркальных символов. `toVisual` вызывает её, а не собирает строку вручную;
  `getReorderSegments` и `getMirroredCharactersMap` не используются и не объявлены.
- Индексы, которые возвращает `bidi-js`, — по кодовым единицам UTF-16. Строку разбирать через `text.split('')`, **не** через `[...text]`: спред режет по кодовым точкам и на суррогатных парах индексы разъедутся.
- Английские и русские PDF после этой подзадачи должны выглядеть в точности как раньше — для LTR-текста весь новый код обязан быть тождественным преобразованием.
- Коммиты — только по явному разрешению пользователя.

```ts
 * Minimal type declarations for bidi-js@1.0.3, which ships no types of its own.
 *
 * Only the three entry points we use are declared. Note that the package's sole
 * export is a factory that must be invoked before any method is available.
 */
declare module 'bidi-js' {
  interface EmbeddingLevels {
    levels: Uint8Array;
    paragraphs: { start: number; end: number; level: number }[];
  }

  interface Bidi {
    getEmbeddingLevels(text: string, explicitDirection?: 'ltr' | 'rtl'): EmbeddingLevels;
    /** Inclusive [start, end] ranges to reverse, in order. */
    getReorderSegments(text: string, levels: EmbeddingLevels, start?: number, end?: number): [number, number][];
    /** Map of UTF-16 index → replacement character (mirrored brackets and the like). */
    getMirroredCharactersMap(text: string, levels: EmbeddingLevels, start?: number, end?: number): Map<number, string>;
  }

  export default function bidiFactory(): Bidi;
}
```

```ts
import bidiFactory from 'bidi-js';
import { Locale } from '../i18n/locale';

export type BaseDir = 'ltr' | 'rtl';

const bidi = bidiFactory();

/** Hebrew, Arabic and the other right-to-left blocks. */
const RTL_CHARS = /[֐-ࣿיִ-﷿ﹰ-﻿]/;

export function containsRtl(text: string): boolean {
  return RTL_CHARS.test(text);
}

/**
 * Rewrites a string from logical order (the order it was typed) into visual
 * order (the order it must be painted).
 *
 * pdfkit draws glyphs strictly left to right in string order and implements no
 * part of the Unicode Bidirectional Algorithm, so Hebrew handed to it verbatim
 * comes out backwards. Reordering here is enough because Hebrew needs no glyph
 * shaping — unlike Arabic, its letters do not join.
 *
 * Indices from bidi-js are UTF-16 code units, hence split('') rather than the
 * spread operator, which would split by code point and shift every index past a
 * surrogate pair.
 */
export function toVisual(text: string, baseDir: BaseDir): string {
  if (!text) return text;

  const levels = bidi.getEmbeddingLevels(text, baseDir);
  const chars = text.split('');

  // Mirrored characters first: the map is keyed by the ORIGINAL index, so it has
  // to be applied before anything moves.
  for (const [index, replacement] of bidi.getMirroredCharactersMap(text, levels)) {
    chars[index] = replacement;
  }

  // Each segment is an inclusive range to reverse in place; they must be applied
  // in the order returned.
  for (const [start, end] of bidi.getReorderSegments(text, levels)) {
    for (let i = start, j = end; i < j; i++, j--) {
      const tmp = chars[i];
      chars[i] = chars[j];
      chars[j] = tmp;
    }
  }

  return chars.join('');
}

/** Explicit locale wins; without one, fall back to what the text itself contains. */
export function baseDirFor(locale: Locale | undefined, text: string): BaseDir {
  if (locale) return locale === 'he' ? 'rtl' : 'ltr';
  return containsRtl(text) ? 'rtl' : 'ltr';
}
```

```ts
/**
 * Greedy word wrap.
 *
 * Exists because the bidirectional algorithm runs per visual line: reordering a
 * whole paragraph and letting the PDF library wrap it afterwards would slice
 * already-reversed text at arbitrary points. So we decide the line breaks first,
 * then reorder each line on its own.
 *
 * `measure` is injected so this stays a pure function — in production it is
 * pdfkit's widthOfString, in tests a stub.
 */
export function wrapToWidth(text: string, maxWidth: number, measure: (s: string) => number): string[] {
  if (!text) return [''];
  if (measure(text) <= maxWidth) return [text];

  const words = text.split(' ');
  const lines: string[] = [];
  let current = '';

  for (const word of words) {
    const candidate = current ? `${current} ${word}` : word;
    if (measure(candidate) <= maxWidth || !current) {
      current = candidate;
      // A single word wider than the column gets its own line rather than being
      // dropped or hyphenated — overflow is more honest than losing content.
      if (!current.includes(' ') && measure(current) > maxWidth) {
        lines.push(current);
        current = '';
      }
    } else {
      lines.push(current);
      current = word;
    }
  }

  if (current) lines.push(current);
  return lines.length > 0 ? lines : [''];
}
```

- [x] **Step 4: Ввести единую точку записи текста**

Добавить в `export.ts` над `renderMarkdown`:

```ts
/**
 * The single place where text reaches the page.
 *
 * For left-to-right output it is a pass-through, so English and Russian PDFs
 * render exactly as they did before. For right-to-left output it wraps the text
 * itself, reorders each resulting line, and aligns to the right — in that order,
 * because the bidirectional algorithm is defined per visual line.
 */
function write(
  doc: PDFKit.PDFDocument,
  text: string,
  baseDir: BaseDir,
  opts: Record<string, unknown> = {},
): void {
  if (baseDir === 'ltr') {
    doc.text(text, opts);
    return;
  }

  const margins = doc.page.margins as { left: number; right: number };
  const indent = typeof opts.indent === 'number' ? opts.indent : 0;
  const width = typeof opts.width === 'number'
    ? opts.width
    : doc.page.width - margins.left - margins.right - indent;

  const lines = wrapToWidth(text, width, (s) => doc.widthOfString(s));
  const visual = lines.map((line) => toVisual(line, 'rtl')).join('\n');

  doc.text(visual, { ...opts, align: 'right', lineBreak: false });
}
```

## Отклонения от плана

- **`getReorderedString` существует** (см. Global Constraints выше). `toVisual` —
  три строки поверх библиотеки вместо ручного разворота сегментов и применения
  карты зеркал. Меньше кода и нет риска перепутать порядок двух операций.
- **Тест переноса иврита был арифметически невыполним.** План ждал
  `['שלום עולם', 'יפה']` при `maxWidth: 70`, но `'שלום עולם'` — девять символов,
  то есть 90 при мерке «10 на символ». Ширина исправлена на 90.
- **`wrapToWidth` в вырожденном случае возвращает `[text]`, а не `['']`.** Ветка
  достижима на строке из одних пробелов; возвращать выдуманную пустую строку
  вместо содержимого — потеря, пусть и незаметная.
- **`write` принимает необязательные `x`/`y`.** Ячейки таблицы позиционируются
  явно, и без этого им пришлось бы звать `doc.text` мимо единой точки записи —
  ровно того места, где живёт всё направление.
- **Зеркалирование колонок считается смещением, а не таблицей перестановки.**
  Колонка сдвинута на сумму ширин тех, что идут *после* неё; массив `order` из
  плана не нужен. Заодно условие рисования разделителя колонок теперь смотрит на
  координату (`x > margins.left`), а не на `colIdx > 0`: при RTL нулевой индекс —
  самая правая колонка, и старое условие пропускало один разделитель и рисовало
  лишний поверх внешней рамки.
- **Добавлена `heightOf`.** При RTL перенос наш, поэтому и высоту строки таблицы
  надо считать по нашим строкам: `heightOfString` меряет перенос pdfkit, которого
  здесь не будет, и ячейка не помещается в свою же строку. В плане этого нет.
- **Отступ при RTL сворачивается в более узкую колонку.** `indent` в pdfkit толкает
  только от левого края — при RTL это дальний конец строки. Проверено: строки
  списка заканчиваются на 530.28 при правом поле 545.28, то есть отступ 15 отсчитан
  справа.
- **`bidi-js` закреплён точной версией** (`1.0.3`, без caret): корректность вывода
  проверена против конкретной реализации UBA, и подтянуть её minor-обновлением
  молча — не то, что хочется от библиотеки, которая переставляет символы.
- **Опции типизированы как `PDFKit.Mixins.TextOptions`**, а не `Record<string, unknown>`:
  все нужные поля (`width`, `indent`, `align`, `lineBreak`, `continued`) там есть,
  и приведения типов не понадобились.
- **Язык добавлен в `frontend/src/lib/api.ts`**, а не в `MessageBubble.tsx`: тела
  запросов живут в `exportToPdf` / `exportToPdfDrive`. `MessageBubble` берёт локаль
  через `useLocale()` и передаёт её дальше.

Способ проверки пришлось выбирать отдельно: `pdftotext` применяет UBA к тексту,

координатам верить можно, содержимому — нет.
